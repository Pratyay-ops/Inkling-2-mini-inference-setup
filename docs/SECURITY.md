# Security model

```
client / gateway ──▶ [TLS edge: tunnel or proxy] ──▶ nginx :8000 ──internal network──▶ vLLM :8000
                                                      per-client keys                   internal key
                                                      path allowlist                    no published port
                                                      rate + concurrency limits         no route out
```

## What protects the endpoint

| Layer | What it does | Where |
|---|---|---|
| Per-client API keys | One random 256-bit key per client (`sk-inkling-` + 64 hex). Add, rotate and revoke take effect on an nginx reload, with no downtime. Logs record the client name, never the key | `scripts/keys.sh`, `nginx/default.conf.template` |
| Key isolation | nginx replaces the client's key with an internal key before forwarding. Client keys never reach vLLM, and the internal key never leaves the box | `upstream-auth.conf` (generated by `scripts/up.sh`) |
| Path allowlist | Only `/v1/chat/completions`, `/v1/completions`, `/v1/responses`, `/v1/models[/<id>]` (GET/POST) and `/health` are reachable. The proxy matches the normalized path and forwards that same path | nginx `location` rules |
| Rate limits | Per key: 20 req/s (burst 40) and 64 concurrent requests. Per IP: 30 req/s, which also throttles key guessing because the key check runs after the limits | `PROXY_*` in `.env` |
| Request limits | 32 MB body cap, 15 s header and 60 s body timeouts (slow-client protection), 1 h response timeout for long generations | `PROXY_MAX_BODY`, `PROXY_READ_TIMEOUT` |
| vLLM isolation | vLLM publishes no port and sits on an `internal` Docker network with no route out, so it can't be reached from the LAN. A key holder also can't make it fetch URLs inside the corporate network (SSRF) | `compose.yaml` |
| Maintenance endpoints | With `CACHE_IDLE_MINUTES > 0`, vLLM runs in dev mode so the cache reaper can pause it, release and wake its KV cache, and reset caches. These endpoints (`/pause`, `/release_kv_cache_memory`, `/wake_up`, `/reset_*_cache`, `/sleep`, …) **have no authentication**. Only the proxy and the reaper are on vLLM's internal network, and the proxy's allowlist never forwards them (404) | `docker/serve.sh`, `docker/cache_reaper.py` |
| Cache lifetime | Prompt caches (prefix and image) are wiped, and KV memory is released, after `CACHE_IDLE_MINUTES` (default 15) with no API requests. A finished or disconnected request's KV is freed immediately in any case | `docker/cache_reaper.py` |
| Container hardening | The proxy runs with a read-only root filesystem and `no-new-privileges`. Secrets are mounted read-only from `~/.config/inkling` (mode 700/600, outside the repo) | `compose.yaml` |

Why not just vLLM's own `--api-key`? It checks the key only on `/v1/*` paths. Tested on 2026-11-24 against this
image (`0.1.dev25855+g7cb5dae22`), with no key, directly on vLLM:

| Route | Result |
|---|---|
| `GET /v1/models` | 401 (checked) |
| `GET /metrics` | 200, Prometheus metrics |
| `POST /tokenize` | 200, tokenizes input |
| `POST /invocations` | **200, a full chat completion**: inference with no key at all |

So exposing vLLM directly with `--api-key` would leave the model open to anyone who knows that route. Through
the proxy, all of these return 404 (covered by `scripts/smoke-test.sh`). vLLM's own key also holds only one
shared key and has no rate limiting, and vLLM's documentation recommends a reverse proxy for anything beyond a
trusted network.

One consequence of the isolation: **image inputs must be sent inline** as base64 `data:` URLs, because vLLM
cannot download `http(s)://` image URLs. OpenAI SDKs and most gateways already send images this way.

## Transport encryption and public access

Plain HTTP is acceptable on localhost or a trusted LAN, but **anything crossing the internet needs TLS**, or
keys and prompts travel in the clear.

**Implemented: Tailscale Funnel** on the host's `tailscaled` (`scripts/funnel.sh`; see the README's "Public access").
Verified on 2026-11-24 over the public path:
- The host makes only outbound connections; no inbound port is opened and nothing listens on the LAN.
- `tailscaled` holds a Let's Encrypt certificate for `<node>.<tailnet>.ts.net` and terminates TLS 1.3
  **on this box**, so Tailscale's relays carry only encrypted bytes.
- It forwards to the proxy's Funnel listener, published only on `127.0.0.1:8001`. That listener trusts
  `X-Forwarded-For`, so per-IP limits apply to each real caller (the log showed the caller's public IP). The
  main listener ignores the header. A local user on this box could set it on `:8001`, but would still need a key.
- Public results: `/health` 200; `/v1/models` 401 without a key; `/metrics` and `/invocations` 404 even with a key.
- **Funnel names are public.** Their certificates appear in Certificate Transparency logs, and an unknown host
  was probing the URL within minutes of it going live. Name the node something neutral
  (`sudo tailscale set --hostname=inkling`) rather than the machine's hostname. Treat the URL as public, never
  as a secret: the keys are what protect it.
- `--operator=$USER` lets that user change this machine's Tailscale settings without sudo. Only grant it to
  the box's admin.

The alternatives considered, cheapest first:

| Option | Cost | Reachable from | TLS | Notes |
|---|---|---|---|---|
| LAN only | $0 | Corporate network | Optional (internal CA / self-signed) | Fine when the gateway is on the same network |
| IT opens a port or gives a public IP, with Let's Encrypt | $0 in fees | Internet | Let's Encrypt (free) | Needs IT approval and a DNS name; the box itself is then directly on the internet |
| **Cloudflare Tunnel** | $0 for the tunnel; a domain is ~$10/yr ($0 if you already have one on Cloudflare) | Internet | Cloudflare edge | Outbound-only (no inbound firewall hole), DDoS protection, optional Cloudflare Access service token as a second credential. Cloudflare drops a request after about 120 s with no response, so the gateway should use `stream: true` for long generations. Run with `BIND_ADDRESS=127.0.0.1` |
| Tailscale (tailnet or Funnel) | $0 on the Personal plan, but that plan is non-commercial only. Company use needs a paid plan (~$8/user/mo, third-party figure) unless the company already has Tailscale | Tailnet devices, or the internet via Funnel | Tailscale | Smallest attack surface when the gateway can join the tailnet |
| ngrok | Free tier is 1 GB/month | Internet | ngrok | Too little traffic for an LLM gateway; paid plans needed |
| Small VPS relay (WireGuard + reverse proxy) | ~$5/month | Internet | Let's Encrypt on the VPS | Full control, but you maintain another public server |

On cost alone, LAN-only is free when the gateway is internal. For internet access, Cloudflare Tunnel is the
cheapest option that is safe for production. Exposing a company machine to the internet will usually need
sign-off from IT/security, so check first.

## Operating the keys

```bash
scripts/keys.sh add gateway        # one key per consumer: the gateway, each app, each person
scripts/keys.sh list               # names, creation time, fingerprint (no keys)
scripts/keys.sh rotate gateway     # new key; the old one stops working immediately
scripts/keys.sh revoke gateway
```

- Store client keys in the gateway's secret store, never in code or chat.
- Rotate when someone leaves or a key may have leaked. The `sk-inkling-` prefix lets GitHub secret scanning
  and similar tools flag committed keys.
- `ops` is the local key used by `smoke-test.sh` and `bench.sh`. Don't hand it out.
- To rotate the internal vLLM key, delete `~/.config/inkling/internal-key` and run `scripts/up.sh`; client keys are unaffected.
- `/health` is unauthenticated on purpose (for load balancers). It returns no model data.
